# アプリ内のお願いの出し方 — 方針と実装計画

作成: 2026-09-23 / 対象: 1.2.0（動作報告の仕組みと同時）/ iOS・iPadOS のみ

アプリが自分から出すお願いと案内には、次の 4 種類がある（1.2.0 で動作報告を足した場合）。
一つずつ見れば控えめでも、別々の決まりで動いているため、続けて出てしまうことがある。
全部を 1 か所で順番と間隔を決める形に作り直す。

| 種類 | 今の出し方 | 形 |
|---|---|---|
| 新機能の案内（例: 音量ダイアル） | 一度だけ。接続直後 | アラート |
| 評価のお願い | 接続成功 3 回以上、初回成功から 2 日以上。バージョンごとに 1 回 | OS のレビューダイアログ（年 3 回まで OS が制限し、出ないこともある） |
| 応援（投げ銭）のお願い | 接続成功 10 回以上、初回成功から 14 日以上。一生に 1 回 | アラート → 応援の画面 |
| 動作報告のお願い（新規） | 未確認の機種で、接続成功 3 回以上（[設計](compatibility-reports-design.md) 3.1） | 画面下の小さな案内 |

## 1. 今の問題

1. **間隔の決まりが「同じ日に重ねない」だけ。**
   評価のお願いの翌日に応援のお願い、その翌日に動作報告……と、3 日続けて何かを頼むことがありうる。
2. **「使った量」を接続の回数で数えている。**
   自動再接続やアプリへの復帰でも数えるため、1 日に何回も増える。
   「3 回」「10 回」が実際には 1〜2 日の利用で達してしまう。
3. **接続した瞬間に出る。**
   アプリを開くのは音量を変えたいときなので、その操作を遮る。Apple も、作業の区切りで頼むよう勧めている。
4. **判定が `ContentView` の中に直接書かれている。**
   種類を足すたびに条件が絡み合う（今も評価と応援が互いの日付を見合っている）。

## 2. 方針

### 2.1 全体の決まり（すべてのお願いと案内に共通）

| 決まり | 値 | 理由 |
|---|---|---|
| 1 回の起動で出すのは 1 つまで | — | 続けて出さない |
| 何かを出したら、次を出すまで空ける日数 | **7 日** | 「頼まれてばかり」と感じさせない |
| 使い始めてから最初の数日は何も頼まない | 利用 **3 日目** から | まず使ってもらう |
| 直近でうまくいかなかったときは頼まない | 過去 24 時間に接続失敗・切断・コマンド失敗があれば見送る | 不満なときに評価や応援を頼まない |
| 出す瞬間 | 接続後、ユーザーが操作を 1 回以上して、**そのあと 5 秒間何も触っていない**とき | 操作の途中で割り込まない |
| 画面にシートやアラートが出ているとき | 出さない（次の機会に回す） | 重ならないようにする |

新機能の案内は「お願い」ではないが、割り込みには違いないので同じ決まりに従う。
ただし、次の 2 点は例外にする。
- 3 日目より前でも出してよい（新しいバージョンに更新した直後に知らせたいため）
- 案内を出した後は、7 日ではなく **2 日** 空ければ次を出してよい

### 2.2 「使った量」は利用日数で数える

接続の回数をやめて、**接続に成功した日の数（利用日数）** を数える。同じ日に何度接続しても 1 日と数える。
あわせて、初めて使った日からの経過日数も見る。

### 2.3 順番

使い始めてからの自然な流れに合わせて、次の順で出す。

**動作報告 → 評価 → 応援**

- **動作報告**（「ちゃんと動きますか？」）: 早めに聞く。動かないならそもそも評価や応援を頼む相手ではないし、
  報告は本人にとっても手間が少ない。
- **評価**（「気に入りましたか？」）: 一通り使ってもらってから。
- **応援**（「開発を支えてもらえますか？」）: 長く使ってくれている人にだけ、一度だけ。

同時に複数の条件がそろったら、この順で 1 つだけ出す。残りは 7 日以上後に回る。

### 2.4 それぞれの条件

| 種類 | 条件（2.1 の全体の決まりに加えて） | 回数 |
|---|---|---|
| 新機能の案内 | その案内をまだ見ていない | 案内ごとに 1 回 |
| 動作報告 | 接続中の機種が未確認（対応機種の一覧で「開発者確認済み」でも「報告済み（問題なく使える 3 件以上）」でもない）。その機種での利用が 3 日以上。この端末からその機種の報告をまだ送っていない | 機種ごとに最大 2 回。案内を閉じたら、同じ機種には 30 日空ける |
| 評価 | 利用 5 日以上、初回から 7 日以上。このバージョンでまだ頼んでいない | バージョンごとに 1 回（OS の年 3 回の制限も効く） |
| 応援 | 利用 10 日以上、初回から 30 日以上、評価を頼んでから 14 日以上。まだ応援していない | 一生に 1 回（設定の「開発を応援する」はいつでも開ける） |

### 2.5 利用者から見た流れの例

新しく使い始めた人（未確認の機種の場合）:

| いつ | 出るもの |
|---|---|
| 1〜2 日目 | 何も出ない |
| 利用 3 日目 | 動作報告の案内（画面下の小さな表示） |
| それから 7 日以上後、利用 5 日以上 | 評価のお願い |
| 評価から 14 日以上後、利用 10 日以上、初回から 30 日以上 | 応援のお願い（1 回だけ） |

確認済みの機種（AVR-X3800H など）の人は、動作報告を飛ばして、2 週目ごろに評価、1 か月以上後に応援になる。
いずれも「そのとき使っていて、うまく動いていて、操作の手が止まったとき」だけ。

### 2.6 今使っている人の扱い（1.1.x から更新したとき）

- 利用日数は記録がないので、次の値から始める: `min(今までの接続成功回数, 初回成功からの日数 + 1)`
- 応援のお願いをすでに出した人（`supportRequestShownDate` がある人）には、二度と出さない。
- 評価のお願いは、新しいバージョンなので条件を満たせば出る。
  ただし更新直後は新機能の案内が先に出るので、評価は 2.1 の間隔を空けた後になる。
- 「最後に何かを出した日」の初期値は、評価と応援のお願いを出した日のうち新しいほう（どちらもなければ未設定）。

## 3. 実装計画

### 3.1 構成

```
Core/Review/
  UsageTracker.swift          利用日数・初回利用日・直近の失敗時刻を記録（UserDefaults）
  InAppPrompt.swift           enum InAppPrompt { case featureIntro(FeatureIntro), compatibility(model:), review, support }
  PromptCoordinator.swift     全体の決まりと順番を持ち、次に出すものを 1 つ返す／出したことを記録する
  ReviewRequestManager.swift  評価の条件だけを持つ（日付の突き合わせは Coordinator に移す）
  SupportRequestManager.swift 応援の条件だけを持つ
  CompatibilityPromptPolicy.swift  動作報告の条件（機種ごとの記録を含む）
```

```swift
@MainActor
enum PromptCoordinator {
    /// 今出してよいものを 1 つ返す（なければ nil）。表示はしない
    static func next(context: PromptContext) -> InAppPrompt?
    /// 実際に出したときに呼ぶ（最後に出した日、種類ごとの記録を更新）
    static func markShown(_ prompt: InAppPrompt)
    /// 動作報告の案内を閉じたとき（機種ごとに 30 日空ける）
    static func markDismissed(_ prompt: InAppPrompt)
}

struct PromptContext {
    var connectedModel: String?      // brand + model
    var modelStatus: ModelStatus     // 対応機種の一覧から（取れなければ unknown）
    var hasPresentedUI: Bool         // シートやアラートが出ているか
    var now: Date = .now
}
```

### 3.2 記録の変更

- `MainViewModel` の `ReviewRequestManager.recordSuccess()` を `UsageTracker.recordSuccessfulConnection(model:)` に置き換える。
  - 利用日数は、日付が変わったときだけ増やす。
  - 機種ごとの利用日数も記録する（動作報告の条件に使う）。
- `MainViewModel` の次の場所で `UsageTracker.recordFailure()` を呼ぶ（直近 24 時間の見送りに使う）:
  - 接続失敗
  - `handleDisconnect`
  - コマンド送信の失敗
- 操作の記録: 今ある `markOperation` で、最後の操作時刻を Coordinator に伝える
  （「操作が 1 回以上あり、5 秒間触っていない」の判定に使う）。

### 3.3 出す場所

- `ContentView` の `onChange(of: vm.connectionStatus)` にある判定をやめ、「区切りを待つタイマー」に置き換える。
  - 接続後、最初の操作が終わってから 5 秒間操作がなければ、`PromptCoordinator.next` を呼ぶ。
  - 返ってきたものに応じて、次のどれかを出して `markShown` する。
    - 案内のアラート
    - `requestReview()`
    - 応援のアラート
    - 動作報告の案内（ダッシュボード下部の表示）
- 動作報告の案内は非モーダルなので、閉じる（×）を押したら `markDismissed` を呼ぶ。
- 音量ダイアルの案内（`hasShownVolumeDialIntroduction`）は `FeatureIntro.volumeDial` として Coordinator に移す。
  既存の保存キーはそのまま使い、見た人には二度と出さない。

### 3.4 確認のしかた（自動テストがないため）

- DEBUG ビルド限定の起動引数を足す。
  - `-promptNow <review|support|compatibility|intro>`: 条件を無視して、区切りのタイミングでその 1 つを出す（見た目の確認用）
  - `-promptDate <yyyy-MM-dd>`: Coordinator が使う「今日」を差し替えて、日数の条件を試す
  - `-promptReset`: お願いの記録を全部消す
- 判定の理由を `DiagnosticsLog` に 1 行残す。例: `prompt: none (cooldown until 2026-10-08)`、`prompt: review`。
  ユーザーから「頼まれすぎ」と言われたときに、送ってもらったログで追える。
- 手で確かめる項目:
  - 同じ日に 2 つ出ない
  - 7 日以内に次が出ない
  - 接続失敗の後 24 時間は出ない
  - 音量を回している最中に出ない
  - 1.1.0 からの更新で、応援のお願いを見た人に再び出ない

### 3.5 作業の順番

1. `UsageTracker` と記録の置き換え（1.1.x からの引き継ぎを含む）
2. `PromptCoordinator` と、評価・応援・音量ダイアルの案内の移行（ここまでは動作報告なしで出せる）
3. 区切りを待つタイマー
4. 動作報告の案内を追加（動作報告の仕組みの段階 4 と一緒に）
5. DEBUG の起動引数と、ログへの記録

## 4. 決めてほしいこと

- 全体の間隔 7 日、応援の「初回から 30 日」は長すぎないか（今は 14 日）。
  - 短くすると応援は増えやすいが、うるさく感じられやすい。
  - 利用者が約 1,200 人の規模なので、まずは控えめに始め、応援の件数を見て縮めるのを勧める。
- 評価のお願いを、今までどおりバージョンごとに出すか。
  - OS が年 3 回に制限するので、実際の上限はそちら。
  - 小さな修正版では頼まない（例: 1.2.0 → 1.2.1 では出さない）、という選択肢もある。
